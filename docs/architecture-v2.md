# XYRO 2.0: воспроизводимый workflow

Планировщик выполняет фазы recon → passive OSINT → DNS/ports → web probing → crawling → discovery → parameters → HTTP/DAST/SSL/XSS/SQLi/auth → verification. Это обычная очередь Python ThreadPoolExecutor, без моделей, обучения, LLM или внешнего управляющего сервиса. Один пользовательский scan имеет не более четырёх исполнителей. При автоматическом режиме два исполнителя включаются от 50 URL или трёх активных хостов, если память и лимиты позволяют. Python CLI с глобальными monkey patches сериализованы.

HTTP/DAST/Dalfox-задачи разбиваются по origin и ограниченным пакетам. Общий бюджет модуля начинает отсчитываться при старте первой задачи. Нативные процессы получают долю rps и concurrency; вложенная работа и ретраи инструмента означают, что это целевой лимит, а не строгий сетевой shaping. Остановка завершает процессы и сохраняет уже полученные результаты. Продолжение использует идентификаторы задач и отпечатки входных данных, фильтров и шаблонов. Пакет Nuclei из 32 шаблонов считается завершённым только после успешного выхода процесса.

DAST получает Burp XML с исходным методом, URL, заголовками и телом запроса. Исходные запросы не подменяются GET-адресами. POST-формы поступают туда только при scan_forms=true. TLS запускается на HTTPS origins. Каталог отмечает протоколы, DAST CVE год, OAST, категории, подпись, слабые matchers и требования Chromium. Файлы upstream не изменяются; SHA256 проверяются при упаковке и перед исполнением; Nuclei получает -dut. OAST выключен без явной настройки собственного Interactsh.

Стадия verify повторяет тот же template_id и исходный input для находки и отмечает reproduced / not_reproduced / pending / error. Это подтверждение воспроизводимости условий детектора, а не доказательство эксплуатируемости. Лимит повторов задаётся отдельно; остальные находки сохраняются pending для продолжения. Выбор шаблона, его отправка движку, выполнение HTTP-запроса и подтверждённая уязвимость — разные события. UI показывает выбранные шаблоны и состояние задач, не объявляет весь каталог проверенным.

Censys обращается только к api.platform.censys.io/v3/global/search/query с Bearer PAT; содержит общий лимит страниц, обработку повторного курсора и ошибок 401/403/429. Данные об IP не расширяют область активного сканирования. Отсутствующий ключ отображается как пропуск. Интеграция тестируется на контрактных fixtures; live API требует пользовательского ключа.

Настройки с токенами и импортированными запросами остаются в приватном каталоге приложения для продолжения. Публичная конфигурация, экспорт и отображаемые журналы маскируют значения. captured-requests.json и Burp XML с сырыми данными не экспортируются. Встроенный сервер слушает только loopback и требует локальный случайный токен, точный Host и Origin.

Dalfox 3.2.3 собирается с небольшим source patch: все production reqwest builders используют tls_certs_only с CA bundle certifi 2026.7.22 (хеш закреплён). SSL_CERT_FILE может явно задать собственный набор CA. Если он отсутствует/невалиден, соединение отклоняется. Никаких danger_accept_invalid_certs для обхода Android JNI. Отдельные tests проверяют HTTPS с доверенным fixture CA и отказ для недоверенного сертификата; те же probes исполняются внутри установленного APK.
